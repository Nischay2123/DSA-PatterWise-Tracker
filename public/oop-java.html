Why classes exist

A class is a named group of properties and functions. In practice, it lets you invent your own data type.

Also in: GFG "Class", Notion "Class & Object"Level: Beginner

The problem classes solve

Storing 5 roll numbers is easy: int[] rno = new int[5]. Storing 5 names is easy too. But "the data of 5 students" means a roll number, a name and marks for each student. Without classes you end up with three parallel arrays and must keep them in sync by hand. Delete student 2 from one array and forget the others, and every student after that has the wrong marks.

Main.java
import java.util.Arrays;

class Student {                 // a new data type: one student, all their data together
    int rno;
    String name;
    float marks;
}

public class Main {
    public static void main(String[] args) {
        // Without a class: three arrays that must stay in sync
        int[] rno = {1, 2};
        String[] name = {"Kunal", "Rahul"};
        float[] marks = {88.5f, 91.0f};
        System.out.println(name[1] + " scored " + marks[1]);

        // With a class: one array of Student objects
        Student[] students = new Student[2];
        System.out.println(Arrays.toString(students));   // slots exist, objects don't yet

        students[0] = new Student();
        students[0].rno = 1;
        students[0].name = "Kunal";
        students[0].marks = 88.5f;
        System.out.println(students[0].name + " scored " + students[0].marks);
    }
}

Trap

new Student[2] creates an array of two empty references, not two students. That's why it prints [null, null]. Calling students[1].name before assigning students[1] = new Student() throws a NullPointerException.

Class vs object

A classic example. Every car has the same properties (that's the class); each car has its own values (those are the objects).

Every object has three properties, a favourite in viva questions:

  • State: the values of its fields right now (rno = 13).
  • Identity: what makes it a different object from another with the same values. Two students named "Kunal" are still two objects.
  • Behaviour: what its methods do (drive(), study()).

Interview tip

"How much memory does a class take?" Almost none on the heap. Its metadata and method code are loaded once into the method area (Metaspace). Heap memory is used only when you create objects.

Objects, new and memory

A variable of a class type never holds the object. It holds a reference to it. Most OOP confusion goes away once that picture is clear.

Also in: Notion "Fields, Methods & Constructors"Level: Beginner

What new does, step by step

Student kunal = new Student(); The type on the left is checked by the compiler; the object on the right is created at runtime. That's why every Java object is said to be allocated dynamically.

Where things live

one and two point to the same object, so a change through one is visible through the other. Method code is stored once per class, not copied into every object.

Main.java
class Student {
    int rno;
    String name;
    float marks = 90;           // a field initialiser replaces the default
}

public class Main {
    public static void main(String[] args) {
        Student one = new Student();
        System.out.println(one.rno + " " + one.name + " " + one.marks);   // defaults

        Student two = one;          // copies the reference, NOT the object
        one.name = "Something something";
        System.out.println(two.name);

        System.out.println(one == two);                  // same object?
        System.out.println(new Student() == new Student());
    }
}

Java is statically typed

You can only use fields the class declares. Python lets you attach kunal.salary on the fly; Java refuses at compile time.

Main.java
class Student { String name; }

public class Main {
    public static void main(String[] args) {
        Student kunal = new Student();
        kunal.salary = 50000;
    }
}

  • The dot is formally a separator, though everyone calls it the dot operator. It links a reference to a member.
  • A local variable must be assigned before use (Student s; s.name doesn't compile). Fields and array slots get default values automatically.
  • Java never shows you the address inside a reference and has no pointer arithmetic. This is a key part of Java's safety compared with C++.
Common simplification

"Objects on the heap, references on the stack" is true for local variables. A reference stored in a field or array element lives on the heap, inside that object or array. Primitive fields are on the heap too. Only locals live in the stack frame.

OOP 1 · Lesson 3

Constructors and this

A constructor is the code that runs when an object is created. this is the object it is running for.

Also in: GFG "Constructor", Notion "this Keyword"Level: Beginner

The rules

  • Same name as the class, and no return type, not even void. Add void and it becomes an ordinary method that never runs on new.
  • If you write no constructor, Java adds a no-argument one. Write any constructor and that free one disappears.
  • Constructors can be overloaded (different parameter lists). This counts as compile-time polymorphism.
  • A constructor can't be abstract, static, final or synchronized. It can be private (used by Singleton).
  • this(...) calls another constructor of the same class. It must be the first statement, so it can't be combined with super(...).

All three kinds, plus chaining

Main.java
class Student {
    int rno;
    String name;
    float marks;

    Student() {                                 // no-arg: delegates to another constructor
        this(13, "default person", 100.0f);
    }

    Student(int rno, String name, float marks) { // parameterised
        this.rno = rno;                         // this.rno = the field, rno = the parameter
        this.name = name;
        this.marks = marks;
    }

    Student(Student other) {                    // copy constructor
        this.rno = other.rno;
        this.name = other.name;
        this.marks = other.marks;
    }

    void greeting() {
        System.out.println("Hello! My name is " + this.name);
    }
}

public class Main {
    public static void main(String[] args) {
        Student kunal = new Student(15, "Kunal", 85.4f);
        Student random = new Student(kunal);
        Student random2 = new Student();

        kunal.greeting();
        random.name = "Rahul Rana";           // the copy is independent
        System.out.println(kunal.name + " | " + random.name + " | " + random2.name);
    }
}
Outputcompiled & run with Java 21
Hello! My name is Kunal
Kunal | Rahul Rana | default person

What this really is

When you call kunal.greeting(), Java runs greeting with this set to kunal. Call rahul.greeting() and the same code runs with this set to rahul. It's Java's version of Python's self, passed for you.

The four everyday uses (from the Notion notes): tell a field apart from a parameter (this.name = name), call another method on the same object, pass the current object to someone else (registry.add(this)), and return it for method chaining (return this;).

Trap · shadowing

Write name = name; in a constructor whose parameter is also called name, and nothing is stored: the parameter is assigned to itself and the field stays null. It compiles without complaint. See the Interview Traps lesson, "Forgetting this in a constructor".

Watch out

this doesn't exist inside a static method, because a static method isn't running for any object.

Common simplification

this(...) is often described as working "like" new Student(...). Treat that as an analogy: this(...) runs the other constructor on the same object, and only one object is created. Also, a copy constructor like the one above is a shallow copy: if a field were an array or list, both objects would share it (see Cloning).

OOP 1 · Lesson 4

Wrapper classes, final and garbage collection

Primitives aren't objects in Java. Wrappers let them act like objects, and that introduces some of the most common interview traps.

Also in: Notion "final Keyword"Level: Beginner → Intermediate

Why primitives don't use new

int, double, boolean and the rest are plain values, kept small and fast. Each has a wrapper class (Integer, Double, Boolean…) that is a real object with methods. Java converts between them automatically: autoboxing (Integer n = 45;) and unboxing (int x = n;). Collections and generics only hold objects, so List<int> isn't allowed; you write List<Integer>.

Java is always pass-by-value

A method gets a copy of whatever you pass. For an object that copy is a copy of the reference. So a method can change the object the reference points to, but it can't make the caller's variable point somewhere else.

Main.java
class Box { int value; Box(int v) { value = v; } }

public class Main {
    static void swap(Integer a, Integer b) {     // only swaps the local copies
        Integer t = a; a = b; b = t;
    }
    static void reassign(Box b) { b = new Box(99); }   // caller never sees this
    static void mutate(Box b)   { b.value = 99; }      // caller DOES see this

    public static void main(String[] args) {
        Integer a = 10, b = 20;
        swap(a, b);
        System.out.println(a + " " + b);

        Box box = new Box(1);
        reassign(box);
        System.out.println(box.value);
        mutate(box);
        System.out.println(box.value);
    }
}

Common misconception

A common explanation says the Integer swap fails "because Integer is a final class". The real reason is pass-by-value, which the Box lines prove: Box isn't final and reassigning still has no effect. final class only means "can't be subclassed". Integer is also immutable, so there's no setter you could use instead.

Trap · Integer cache

Integer a = 127, b = 127; a == b is true, but with 128 it's false. Autoboxing reuses cached objects for −128 to 127. Compare wrappers with equals(). See "Integer caching" in Interview Traps.

final

Main.java
class A {
    final int num;                 // a "blank final": no value yet...
    String name;
    A(String name) {
        this.name = name;
        this.num = 10;             // ...so every constructor must assign it exactly once
    }
}

public class Main {
    static final int MAX_MARKS = 100;          // constant: ALL_CAPS by convention

    public static void main(String[] args) {
        final A kunal = new A("Kunal");
        kunal.name = "other name";             // allowed: the OBJECT can change
        // kunal = new A("new object");        // not allowed: the REFERENCE can't
        System.out.println(kunal.name + " " + kunal.num + " " + MAX_MARKS);
    }
}
Outputcompiled & run with Java 21
other name 10 100
  • final variable: assigned once. For a primitive that freezes the value; for a reference it freezes only which object, not the object's contents.
  • final field: must be assigned by the end of every constructor (or in its declaration or an initialiser block). Older tutorials say "must be initialised when declared", which is stricter than Java requires.
  • final method: can't be overridden. final class: can't be extended (String, Integer). Both come back in OOP 3.
  • Notion's one-liner: final means "this can't change in this particular way". A final reference doesn't make an object immutable.

Garbage collection

You never delete objects in Java. When nothing references an object any more, the garbage collector may reclaim its memory, at a time the JVM chooses. Create objects in a loop and you will see that the collector doesn't run at all for small workloads.

Older Java vs. modern Java

Older Java code uses finalize() as a destructor-like hook. It has been deprecated since Java 9 and marked for removal since Java 18 (JEP 421): it may never run, it slows the collector, and it isn't a destructor. To release files, sockets or connections, use try-with-resources with AutoCloseable (or java.lang.ref.Cleaner as a safety net). In an interview, say exactly that. Likewise, new Integer(45) is deprecated; use autoboxing or Integer.valueOf(45).

Main.java
class Connection implements AutoCloseable {
    Connection() { System.out.println("open"); }
    void query() { System.out.println("query"); }
    @Override public void close() { System.out.println("closed, guaranteed"); }
}

public class Main {
    public static void main(String[] args) {
        try (Connection c = new Connection()) {   // close() runs even if query() throws
            c.query();
        }
    }
}

Packages and imports

A package is a folder for classes. It lets two classes share a name, and it is the boundary that access modifiers respect.

Also in: Notion "Packages & Imports"Level: Beginner

Why packages exist

You can't have two files called Greeting.java in one folder. Put them in different packages and both can exist: com.example.packages.a.Greeting and com.example.packages.b.Greeting. Their full names differ.

  • The package name must match the folder path exactly, case included: package com.example.a; lives in com/example/a/.
  • Convention: start with your domain reversed (com.google…, in.example…) so names never clash across companies.
  • IntelliJ shows com.example as one "compacted" folder. On disk it's still two nested folders.
com/example/packages/a/Greeting.java
package com.example.packages.a;

import static com.example.packages.b.Message.message;   // static import: use message() directly

public class Greeting {
    public static void main(String[] args) {
        System.out.println("Hello world");
        message();                        // instead of Message.message()
    }
}

What import really does

  • import only lets you write the short name. It doesn't load, copy or include anything; the compiled class still uses the full name. You could skip imports and type java.util.ArrayList everywhere.
  • import java.util.*; imports the classes in java.util, not its sub-packages like java.util.function.
  • java.lang (String, System, Math, Object, wrappers) is imported automatically.
  • From another package you can only use what is declared public (or protected, through inheritance; see Access Control).

The static keyword

Instance members have one copy per object. Static members have one copy per class, shared by every object.

Also in: Notion "static Keyword"Level: Beginner → Intermediate

Each human has their own name, but population is a fact about humans as a whole.

Main.java
class Human {
    static long population;     // one shared copy, default 0
    String name;                // one copy per object

    Human(String name) {
        this.name = name;
        Human.population++;     // every new object bumps the shared counter
    }
}

public class Main {
    public static void main(String[] args) {
        System.out.println(Human.population);     // usable before any object exists
        Human kunal = new Human("Kunal");
        Human rahul = new Human("Rahul");
        Human arpit = new Human("Arpit");
        System.out.println(Human.population);
        System.out.println(kunal.population);     // works, but misleading: IDEs warn
    }
}

Why is main static?

The JVM has to call main before any object of your class exists. A static method can be called on the class itself.

Static blocks

A static { } block runs once, when the class is initialised, which happens on its first active use (creating an object, or touching a static member). It never runs again for later objects. Several static blocks run top to bottom.

Main.java
class StaticBlock {
    static int a = 4;
    static int b;

    static {
        System.out.println("I am in static block");
        b = a * 5;
    }
}

public class Main {
    public static void main(String[] args) {
        StaticBlock obj = new StaticBlock();
        System.out.println(StaticBlock.a + " " + StaticBlock.b);
        StaticBlock.b += 3;
        StaticBlock obj2 = new StaticBlock();      // no second "static block" line
        System.out.println(StaticBlock.a + " " + StaticBlock.b);
    }
}

Trap · "static means shared" is wrong here

This trips people up: a static nested class does not make its objects share fields. a.name and b.name above stay different. static only means the class doesn't depend on an outer object. Also, only nested classes can be static; static class A {} at the top level doesn't compile.

  • Creating a non-static inner class from main fails, because there's no outer object. See the trap "Creating an inner class from main".
  • Local and anonymous classes (and lambdas) can only use local variables that are effectively final, meaning never reassigned.
  • An inner class keeps a hidden reference to its outer object. Holding on to an inner object therefore keeps the outer object alive, a classic memory leak in Android code.
Older Java vs. modern Java

Before Java 16, only static nested classes could declare static members. Since Java 16 (JEP 395), inner classes can declare static members too.

Singleton, and how println prints an object

Two short topics that end OOP 2 and show up in almost every fresher interview.

Level: Intermediate

How System.out.println(obj) works

  • System is a class, out is a public static final PrintStream field in it, and println is a method of PrintStream. That's why you never create a System object.
  • println(Object x) calls String.valueOf(x), which calls x.toString() (or prints null).
  • The default Object.toString() gives ClassName@ plus the hash code in hex. Override toString() to print something useful.
Main.java
class Plain { int num = 54; }

class Pretty {
    int num = 54;
    @Override public String toString() { return "Pretty{num=" + num + "}"; }
}

public class Main {
    public static void main(String[] args) {
        System.out.println(new Plain());     // ClassName@hash
        System.out.println(new Pretty());
        Pretty p = null;
        System.out.println(p);               // String.valueOf handles null
    }
}

Singleton: exactly one object

The classic recipe, which interviewers expect you to write from memory:

  • A private constructor, so nobody outside can call new.
  • A private static field that holds the one instance.
  • A public static getInstance(). It has to be static because no object exists yet to call it on.
Main.java
class Singleton {
    private static Singleton instance;          // lazily created

    private Singleton() {
        System.out.println("constructor runs once");
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}

public class Main {
    public static void main(String[] args) {
        Singleton obj1 = Singleton.getInstance();
        Singleton obj2 = Singleton.getInstance();
        Singleton obj3 = Singleton.getInstance();
        System.out.println(obj1 == obj2 && obj2 == obj3);   // three references, one object
    }
}

Make it thread-safe

The lazy version above is not thread-safe: two threads can both see null and create two objects. Interviewers often ask for a fix. The three standard answers are below. The enum version also survives serialization and reflection attacks, which is why Effective Java recommends it.

Main.java
class Holder {                              // 1. Bill Pugh / holder idiom: lazy and thread-safe
    private Holder() {}
    private static class Box { static final Holder INSTANCE = new Holder(); }
    static Holder getInstance() { return Box.INSTANCE; }
}

enum Registry {                             // 2. enum singleton: the simplest safe version
    INSTANCE;
    int count;
}

class Dcl {                                 // 3. double-checked locking: needs volatile
    private static volatile Dcl instance;
    private Dcl() {}
    static Dcl getInstance() {
        if (instance == null) {
            synchronized (Dcl.class) {
                if (instance == null) instance = new Dcl();
            }
        }
        return instance;
    }
}

public class Main {
    public static void main(String[] args) {
        System.out.println(Holder.getInstance() == Holder.getInstance());
        Registry.INSTANCE.count++;
        System.out.println(Registry.INSTANCE.count);
        System.out.println(Dcl.getInstance() == Dcl.getInstance());
    }
}

Inheritance

A child class gets everything its parent has, then adds its own. Use it only when the child truly is a kind of the parent.

Also in: GFG "Inheritance", Notion "Inheritance"Level: Beginner → Intermediate
Analogy

Parents pass money, traits and values to their children; the children add things of their own. In code, BoxWeight extends Box: every BoxWeight has l, h, w from Box, plus its own weight.

UML convention: the hollow triangle sits on the parent. A child knows its parent; a parent knows nothing about its children, and siblings know nothing about each other.

Main.java
class Box {
    double l, h, w;

    Box() { this.l = this.h = this.w = -1; }        // "not set yet"
    Box(double side) { this.l = this.h = this.w = side; }
    Box(double l, double h, double w) {
        System.out.println("Box class constructor");
        this.l = l; this.h = h; this.w = w;
    }
}

class BoxWeight extends Box {
    double weight;

    BoxWeight() { this.weight = -1; }               // super() is inserted for you
    BoxWeight(double l, double h, double w, double weight) {
        super(l, h, w);                             // the parent sets ITS fields
        this.weight = weight;                       // the child sets its own
    }
}

public class Main {
    public static void main(String[] args) {
        BoxWeight b1 = new BoxWeight();
        System.out.println(b1.l + " " + b1.h + " " + b1.w + " " + b1.weight);
        BoxWeight b2 = new BoxWeight(2, 3, 4, 8);
        System.out.println(b2.l + " " + b2.h + " " + b2.w + " " + b2.weight);
    }
}

What a child does and doesn't get

  • Private members are part of the child object but the child's code can't touch them. Use the parent's public or protected methods (getL()). Put simply: the subclass includes them but cannot access them.
  • Constructors are never inherited. The child calls them with super(...).
  • Static members are inherited (accessible) but hidden, not overridden.
  • Every class without extends silently extends java.lang.Object. That's not multiple inheritance: Object just sits at the top of every chain.

class Box {

        System.out.println(getL());   // fine: through a public method
        System.out.println(l);        // not accessible from the child
    }
}

public class Main {
    public static void main(String[] args) { new BoxWeight().show(); }

Why no multiple inheritance of classes?

Thought experiment: class C extends A, B, and both A and B have a field n. What does c.n print? Nobody can say, so Java forbids it. Interfaces get around this because they carry no instance state; their default-method clashes have strict rules (see Interfaces).

Use inheritance only for a real "is-a"

Car extends Engine is wrong: a car has an engine. That's composition (OOP 5). GeeksforGeeks' interview list also notes the costs of inheritance: tight coupling between parent and child, and a fragile hierarchy when the parent changes.

Parent reference, child object

The single most important rule in OOP 3. Get this right and most polymorphism questions become easy.

Level: Intermediate · asked constantly
The rule

The reference type (left side) decides what you can call. The object type (right side) decides which version runs. The first is checked by the compiler; the second is decided by the JVM at runtime.

Think of the reference as a window shaped like its own type. The whole BoxWeight is there, but a Box-shaped window only shows the Box part, and an overridden method still runs the child's code.

Main.java
class Box {
    double l = 2, h = 3, w = 4;
    String describe() { return "plain box"; }
}

class BoxWeight extends Box {
    double weight = 8;
    @Override String describe() { return "box weighing " + weight; }
    void onlyInChild() { System.out.println("child-only method"); }
}

public class Main {
    public static void main(String[] args) {
        Box box = new BoxWeight();             // parent reference, child object: OK
        System.out.println(box.w);             // Box declares w
        System.out.println(box.describe());    // runtime picks BoxWeight's version
        // box.weight; box.onlyInChild();      // compile errors: Box doesn't declare them

        if (box instanceof BoxWeight bw) {      // check, then cast (pattern matching, Java 16+)
            System.out.println(bw.weight);
            bw.onlyInChild();
        }
    }
}

Trap · forcing it with a cast

BoxWeight b = (BoxWeight) new Box(); compiles, because a Box might be a BoxWeight. At runtime the JVM checks the actual object and throws ClassCastException. Always check with instanceof before downcasting. See "Downcasting to the wrong type".

Trap · fields are not polymorphic

If the child declares a field with the same name as the parent's, parentRef.field reads the parent's field. Only methods are chosen at runtime. See "Are fields polymorphic?".

  • Upcasting (child to parent reference) is automatic and always safe.
  • Downcasting (parent to child reference) needs an explicit cast and can fail at runtime.
  • This rule is why List<String> names = new ArrayList<>(); is good style: code against the interface, and swap the implementation later.

super and the order things run in

super is how a child reaches its immediate parent. Constructors always finish parent-first, because a parent knows nothing about its children.

Level: Intermediate

Three uses of super

  • super(args): call the immediate parent's constructor. It must be the first statement. If you don't write one, Java inserts super(), so a parent with no no-arg constructor forces every child to call super(args) explicitly.
  • super.method(): run the parent's version of a method you overrode.
  • super.field: reach a parent field hidden by a child field of the same name.
Main.java
class Box {
    double l, h, w;
    Box(double l, double h, double w) {
        this.l = l; this.h = h; this.w = w;
        System.out.println("1. Box constructor");
    }
    String info() { return "Box " + l + "x" + h + "x" + w; }
}

class BoxWeight extends Box {
    double weight;
    BoxWeight(double l, double h, double w, double weight) {
        super(l, h, w);                         // immediate parent only
        this.weight = weight;
        System.out.println("2. BoxWeight constructor");
    }
    @Override String info() { return super.info() + ", " + weight + "kg"; }
}

class BoxPrice extends BoxWeight {
    double cost;
    BoxPrice(double l, double h, double w, double weight, double cost) {
        super(l, h, w, weight);                 // BoxWeight passes the rest up
        this.cost = cost;
        System.out.println("3. BoxPrice constructor");
    }
    @Override String info() { return super.info() + ", Rs " + cost; }
}

public class Main {
    public static void main(String[] args) {
        BoxPrice p = new BoxPrice(5, 8, 20, 9, 400);
        System.out.println(p.info());
    }
}

No super.super

You can only go one level up. BoxPrice can't skip BoxWeight to reach Box directly; it relies on BoxWeight to pass things up.

The full initialisation order

Steps 4–7 happen because the child constructor's first act is super(...). The child's own fields aren't set until step 6.

Trap · overridable method in a constructor

If the parent constructor calls a method the child overrides, the child's version runs at step 5, before the child's fields are set at step 6, so it sees null or 0. See "Calling an overridable method from a constructor" and "Initialisation order across a hierarchy" in Interview Traps.

Modern Java

"super(...) must be the first statement" holds up to Java 24. Java 25's flexible constructor bodies (JEP 513) allow statements before super(...), such as validating arguments, as long as they don't use this. For interviews, give the classic rule and mention the change.

Overloading

Same method name, different number, type or order of parameters. The return type alone doesn't count, because the compiler couldn't tell which method you meant. Java doesn't let you overload operators; + for String concatenation is built into the language.

@Override

The annotation asks the compiler to check that you really override something. Misspell the name or change a parameter, and you get an error instead of a silent new method.

Overriding rules interviewers probe

  • Access can stay the same or widen, never narrow: overriding a public method as protected doesn't compile.
  • An override can't throw broader checked exceptions than the parent method declares.
  • The return type may be a subtype (covariant return): if the parent returns Animal, the child may return Dog.
  • private methods aren't inherited, so they can't be overridden. A child method with the same name is a brand-new method.
  • static methods can't be overridden, only hidden. final methods can't be overridden at all.
Main.java
class Box {
    static void greeting() { System.out.println("Hey, I am in Box greeting"); }
    Box create() { return new Box(); }
}
class BoxWeight extends Box {
    static void greeting() { System.out.println("Hey, I am in BoxWeight greeting"); }  // hides
    @Override BoxWeight create() { return new BoxWeight(); }   // covariant return type
}

public class Main {
    public static void main(String[] args) {
        Box b = new BoxWeight();
        b.greeting();                                      // chosen by the reference type
        BoxWeight.greeting();
        System.out.println(b.create().getClass().getSimpleName());
    }
}

Older Java vs. modern Java

Many notes say that for static methods "the parent version will run always". More precisely, the version is chosen by the reference or class name: BoxWeight.greeting() runs the child's. That's method hiding. Older advice also says final methods are faster because they can be inlined. Today's JIT inlines non-final methods too, so use final as a design decision, not a speed trick.

final and binding

  • Early (static) binding, decided at compile time: overloaded methods, and static, private and final methods, plus all field access.
  • Late (dynamic) binding, decided at runtime: overridden instance methods.
  • A final class can't be extended, which makes all its methods effectively final. abstract and final together on a class is illegal.

Most learners confuse these two. They're related, and interviewers love asking you to tell them apart.

Data hiding is narrower than both: it's about data security, making fields private. Encapsulation achieves data hiding, and also bundles the behaviour that uses the data.

Analogy

ArrayList is both. Abstraction: you call add, get and remove without caring how they work. Encapsulation: its internal array is private, so you can't break it from outside, and only its methods can resize it.

Encapsulation done properly

A getter and setter for every field is not encapsulation by itself. The point is that the object enforces its own rules. The Notion notes put it well: don't give direct access to your data; give controlled ways to interact with it. Some fields shouldn't have a getter at all.

Main.java
class BankAccount {
    private double balance;              // nobody outside can set this directly
    private final String pin;            // no getter at all, on purpose

    BankAccount(double opening, String pin) {
        if (opening < 0) throw new IllegalArgumentException("opening balance can't be negative");
        this.balance = opening;
        this.pin = pin;
    }

    public double getBalance() { return balance; }

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("deposit must be positive");
        balance += amount;
    }

    public boolean withdraw(double amount, String pin) {
        if (!this.pin.equals(pin) || amount <= 0 || amount > balance) return false;
        balance -= amount;
        return true;
    }
}

public class Main {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount(1000, "4321");
        acc.deposit(500);
        System.out.println(acc.withdraw(200, "0000"));    // wrong PIN
        System.out.println(acc.withdraw(-50, "4321"));    // negative amount is rejected
        System.out.println(acc.withdraw(200, "4321"));
        System.out.println(acc.getBalance());
        // acc.balance = -5000;   // compile error: balance is private
    }
}

The important point about protected

This rule deserves its own section. In a different package, a subclass can use a protected member only through its own type: inherited (display(), this.display()) or on a Derived reference. It can't use it on a plain Base object.

The reasoning: sibling subclasses know nothing about each other. Letting Derived poke another subclass's protected internals through a Base reference would be unsafe.

two/Derived.java
package two;
import one.Base;

public class Derived extends Base {
    void show() {
        display();                 // OK: inherited
        this.display();            // OK
        new Derived().display();   // OK: a Derived reference
        new Base().display();      // compile error: display() has protected access in Base
    }
}

The Interview Traps lesson compiles exactly this case across two real packages: "protected from another package".

When to use which

  • private: the default choice for fields, and for helper methods that are internal details.
  • public: the operations other code should use. Making everything public is very dangerous.
  • protected: hooks meant for subclasses to use or override.
  • default: classes and helpers shared inside one package only.
Interview follow-ups

A top-level class can only be public or default, never private or protected. Only one public top-level class is allowed per file, and the file must share its name. An override can't make a method less visible (see "Making an overriding method less visible").

== vs equals()

  • == on references asks "are these the same object?". On primitives it compares values.
  • equals() asks "do these mean the same thing?", but only if the class overrides it. String, the wrappers and the collections all do.

The contract, and why it exists

The contract: if a.equals(b) then a.hashCode() == b.hashCode(). The reverse isn't required, because different objects may share a hash code (a collision).

Main.java
import java.util.*;

class Student {
    final int roll;
    final String name;
    Student(int roll, String name) { this.roll = roll; this.name = name; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;                       // same object
        if (!(o instanceof Student s)) return false;      // handles null and other types
        return roll == s.roll && Objects.equals(name, s.name);
    }
    @Override public int hashCode() { return Objects.hash(roll, name); }   // same fields as equals
    @Override public String toString() { return "Student(" + roll + ", " + name + ")"; }
}

public class Main {
    public static void main(String[] args) {
        Student a = new Student(12, "Kunal");
        Student b = new Student(12, "Kunal");
        System.out.println(a == b);                 // two objects
        System.out.println(a.equals(b));            // same meaning
        System.out.println(new HashSet<>(List.of(a, b)).size());
        System.out.println(a.equals(null));
        System.out.println(a.getClass().getName() + " " + (a instanceof Object));
    }
}

Common mix-up

Many notes say "an interface can have only abstract methods" and that "from Java 8, an abstract class can have default and static methods". That's swapped. Interfaces gained default and static methods in Java 8 and private methods in Java 9. Abstract classes could always have static methods, and default isn't a keyword for them.

The diamond problem, Java edition

Solid arrows mean extends; dashed arrows mean implements. With classes this shape is impossible in Java. With default methods it can happen, so Java has three rules.

  1. A class always wins. A method inherited from a superclass beats any interface default.
  2. The more specific interface wins. If B extends A and both define hello(), B's version is used.
  3. Otherwise you must choose. Override the method and, if you like, delegate with B.super.hello(). If you don't override, it's a compile error (see "Two interfaces with the same default method").
Main.java
interface A { default void hello() { System.out.println("Hello from A"); } }
interface B extends A { @Override default void hello() { System.out.println("Hello from B"); } }
interface C extends A { @Override default void hello() { System.out.println("Hello from C"); } }

class D implements B, C {
    @Override public void hello() {       // rule 3: we must resolve it ourselves
        B.super.hello();
        C.super.hello();
        System.out.println("Hello from D");
    }
}

class Base { public void hello() { System.out.println("Hello from class Base"); } }
class E extends Base implements B { }     // rule 1: the class method wins, no override needed

class F implements A, B { }               // rule 2: B is more specific than A

public class Main {
    public static void main(String[] args) {
        new D().hello();
        new E().hello();
        new F().hello();
    }
}

Step 1: an ArrayList that grows

An ArrayList is an ordinary array with encapsulation around it. When the array fills up, it creates a bigger one (here it doubles) and copies everything across. Copying is occasional, so adding is constant time on average (amortised O(1)).

Main.java
import java.util.Arrays;

class CustomArrayList {
    private int[] data = new int[2];     // private: only the methods can touch it
    private int size = 0;                // also the index of the next free slot

    void add(int num) {
        if (size == data.length) {       // full: double and copy
            data = Arrays.copyOf(data, data.length * 2);
            System.out.println("resized to " + data.length);
        }
        data[size++] = num;
    }
    int remove() { return data[--size]; }
    int get(int i) { return data[i]; }
    int size() { return size; }
}

public class Main {
    public static void main(String[] args) {
        CustomArrayList list = new CustomArrayList();
        for (int i = 1; i <= 5; i++) list.add(i * 10);
        System.out.println(list.get(4) + " size=" + list.size());
        System.out.println(list.remove() + " size=" + list.size());
    }
}

Step 2: make it generic

To store Strings, Students or anything else, pass the type in as a parameter: CustomGenArrayList<T>. Generics are also called "parameterised types".

Main.java
import java.util.Arrays;

class CustomGenArrayList<T> {
    private Object[] data = new Object[2];     // can't write new T[2]
    private int size = 0;

    void add(T item) {
        if (size == data.length) data = Arrays.copyOf(data, size * 2);
        data[size++] = item;
    }
    @SuppressWarnings("unchecked")
    T get(int i) { return (T) data[i]; }       // the cast is safe: only T ever goes in

    T remove() {
        @SuppressWarnings("unchecked") T item = (T) data[--size];
        data[size] = null;                     // let the GC collect it (easy to forget)
        return item;
    }
}

public class Main {
    public static void main(String[] args) {
        CustomGenArrayList<String> names = new CustomGenArrayList<>();
        names.add("Kunal");
        names.add("Rahul");
        names.add("Arpit");
        String first = names.get(0);           // no cast needed by the caller
        System.out.println(first + " " + names.remove());

The rules of generics

  • No primitives: List<int> isn't allowed. Use List<Integer> and let autoboxing do the work.
  • No new T() or new T[]: at runtime Java doesn't know what T is. Store Object[] and cast, as above.
  • Type erasure: generics are checked by the compiler and then erased. The bytecode has plain Object (or the bound), so List<String> and List<Integer> are the same class at runtime.
  • Because of erasure you can't overload void f(List<String>) with void f(List<Integer>): both erase to f(List).

import java.util.*;

public class Main {

        List<Integer> b = new ArrayList<>();
        System.out.println(a.getClass() == b.getClass());   // erased: same runtime class
    }
}

Cloning: shallow vs deep copy

Copying an object is easy. Copying the objects inside it is the part people forget.

Also in: GFG Q29Level: Intermediate → Advanced

Both versions copy the primitive and String fields. Strings are shared too, but they're immutable, so sharing them is harmless. Only the mutable array differs.

Main.java
import java.util.Arrays;

class Human implements Cloneable {             // marker interface: allows clone()
    int age;
    String name;
    int[] arr;

    Human(int age, String name) {
        this.age = age; this.name = name;
        this.arr = new int[]{3, 4, 5};
    }

    Human shallowCopy() throws CloneNotSupportedException {
        return (Human) super.clone();          // copies the fields as they are
    }

    @Override public Human clone() throws CloneNotSupportedException {
        Human twin = (Human) super.clone();
        twin.arr = arr.clone();                // deep: give the twin its own array
        return twin;
    }
}

public class Main {
    public static void main(String[] args) throws CloneNotSupportedException {
        Human kunal = new Human(34, "Kunal");

        Human shallow = kunal.shallowCopy();
        shallow.arr[0] = 100;
        System.out.println("after shallow: " + Arrays.toString(kunal.arr));

        kunal.arr[0] = 3;                      // reset
        Human deep = kunal.clone();
        deep.arr[0] = 100;
        System.out.println("after deep:    " + Arrays.toString(kunal.arr));
        System.out.println(deep.name + " " + (deep != kunal));
    }
}

Enums are classes

An enum is a class with a fixed set of objects created for you, one per constant. Because it's a class, it can have fields, constructors, methods and interfaces.

Why not public static final String MONDAY = "Monday"? Because then any string can sneak in where a day is expected. With an enum, the compiler accepts only the real constants: type safety, as the Notion notes put it.

Main.java
interface Greeter { void hello(); }

enum Week implements Greeter {                 // enums can implement interfaces
    Monday(true), Tuesday(true), Wednesday(true), Thursday(true),
    Friday(true), Saturday(false), Sunday(false);

    private final boolean working;             // enums can have fields

            if (!day.isWorking()) System.out.println(day + " is a holiday");

            case Saturday, Sunday -> System.out.println("weekend");
            default -> System.out.println("weekday");

        System.out.println(week == Week.Monday);   // compare enums with ==

Rules to remember

  • Each constant is a public static final object of the enum's type, created exactly once, when the enum is first used.
  • The constructor is always private. Writing no modifier doesn't make it package-private, and public or protected is a compile error. Nobody can create extra objects; that's why an enum makes a perfect Singleton.
  • An enum can't extends anything, because it already extends java.lang.Enum. It can implement interfaces, and you can't subclass an enum.
  • values() gives every constant in order, ordinal() gives the position starting at 0, and valueOf("Monday") turns a name into the constant.

Sealed classes: a closed family

sealed lists exactly which classes may extend a class or interface. Each permitted subclass must say how it continues: final (no further children), sealed (its own closed list) or non-sealed (open again).

Main.java
sealed interface Shape permits Circle, Square, Rectangle {}
record Circle(double r) implements Shape {}                 // records are final
record Square(double side) implements Shape {}
final class Rectangle implements Shape {
    final double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }
}

public class Main {
    static double area(Shape s) {
        return switch (s) {                       // Java 21 pattern switch
            case Circle c    -> Math.PI * c.r() * c.r();
            case Square sq   -> sq.side() * sq.side();
            case Rectangle r -> r.w * r.h;
            // no default needed: the compiler knows these are ALL the shapes
        };
    }
    public static void main(String[] args) {
        System.out.printf("%.2f %.2f %.2f%n", area(new Circle(1)), area(new Square(3)), area(new Rectangle(2, 5)));
    }
}

Immutability, SOLID and design habits

What interviewers at product companies actually check once you know the syntax: can you design classes that are hard to misuse?

Recipe for an immutable class

  • Make the class final, so no subclass can add mutable behaviour.
  • Make every field private final, and set them all in the constructor.
  • Provide no setters. A "change" returns a new object (withAge(26)), as String and LocalDate do.
  • Defensively copy mutable inputs on the way in, and never hand out a mutable field on the way out.
Main.java
import java.util.*;

final class Employee {
    private final String name;
    private final int age;
    private final List<String> skills;

    Employee(String name, int age, List<String> skills) {
        this.name = name;
        this.age = age;
        this.skills = List.copyOf(skills);        // copy in (and it's unmodifiable)
    }
    String name() { return name; }
    List<String> skills() { return skills; }      // safe: List.copyOf can't be modified
    Employee withAge(int newAge) { return new Employee(name, newAge, skills); }
    @Override public String toString() { return name + "(" + age + ") " + skills; }
}

public class Main {
    public static void main(String[] args) {
        List<String> s = new ArrayList<>(List.of("Java"));
        Employee e = new Employee("Kunal", 25, s);
        s.add("Hacking");                          // doesn't leak in
        Employee older = e.withAge(26);
        System.out.println(e + " | " + older);
        try {
            e.skills().add("Go");
        } catch (UnsupportedOperationException ex) {
            System.out.println("skills can't be modified from outside");
        }
    }
}
Outputcompiled & run with Java 21
Kunal(25) [Java] | Kunal(26) [Java]
skills can't be modified from outside

Why bother: immutable objects can be shared between threads without locks, are safe as HashMap keys, and can never be in a half-updated state.

Seven habits from the Notion notes

  • Keep fields private.
  • Let the object enforce its own rules: account.withdraw(500), never account.balance = -500.
  • Prefer immutability; add setters only when something truly must change.
  • Keep classes focused. A "User + Payment + Email + DB" class is a god object.
  • Program to interfaces: List<String> names = new ArrayList<>();
  • Prefer composition to deep hierarchies. If a hierarchy is more than about three levels deep, reconsider it.
  • Aim for high cohesion (a class's parts belong together) and low coupling (classes depend on each other as little as possible).

30 interview questions

Built from the GeeksforGeeks interview list (rewritten for Java, with corrections), frequently asked interview topics, and common senior-level follow-ups. Each answer is short enough to say out loud.

BASIC fresherINTERMEDIATE 1–3 yearsADVANCED senior and design rounds

Basic

B1. What is OOP, and how is it different from procedural programming?

OOP organises a program around objects that bundle data with the methods that work on it. Procedural code keeps data and functions separate and passes data around. OOP gives you encapsulation to protect data, inheritance and composition for reuse, and polymorphism so new types can be added without rewriting old code. The cost: more design up front, and more structure than a small script needs.

B2. Class vs object? How much memory does a class take?

A class is a blueprint, a logical construct; an object is an instance of it, a physical reality on the heap. The class takes no heap memory itself: its metadata and method code are loaded once into the method area. Every new allocates heap memory for one object's fields.

B3. What are the four pillars?

Encapsulation (bundle data and methods, restrict access), inheritance (reuse a parent's members: is-a), polymorphism (one call, many behaviours: overloading and overriding), and abstraction (expose what, hide how: abstract classes and interfaces).

B4. Encapsulation vs abstraction vs data hiding?

Abstraction solves design-level problems: it decides what an object exposes. Encapsulation solves implementation-level problems: it wraps the data and controls access to it. Data hiding is the narrow security part, making fields private. Encapsulation achieves data hiding.

B5. What is a constructor? What kinds are there? Can it be overloaded, private or inherited?

A constructor initialises a new object. It has the class name and no return type. Kinds: default (supplied by Java only if you write none), no-arg, parameterised, copy (you write it yourself), and private (Singleton, factories). Constructors can be overloaded and chained with this(...). They're never inherited: a child calls them with super(...).

B6. Is Java pass-by-value or pass-by-reference?

Always pass-by-value. For objects the value copied is the reference, so a method can change the object's fields but can't make the caller's variable point to a different object. That's why swapping two Integer parameters inside a method has no effect.

B7. Overloading vs overriding?

Overloading: same name, different parameter list, usually in one class, chosen at compile time from the declared types. The return type alone can't distinguish overloads. Overriding: a child redefines a parent's method with the same signature, chosen at runtime from the actual object. It can't reduce visibility or throw broader checked exceptions, and it may use a covariant return type.

B8. Explain the access modifiers.

private: the class only. default: the package. protected: the package plus subclasses elsewhere, but in another package only through the subclass's own type, never on a plain parent object. public: everyone. Top-level classes can only be public or default.

B9. Can you call a method without creating an object?

Yes, if it's static: Math.max(2, 3), or main itself. Static methods belong to the class, can't use this, and can only reach instance members through an object reference.

B10. Which kinds of inheritance does Java support, and why not multiple?

Single, multilevel and hierarchical, with classes. Multiple and hybrid only through interfaces. With two parent classes that both define the same field or method, a call would be ambiguous, so Java forbids it. Interfaces carry no instance state, and their default-method clashes must be resolved explicitly.

Intermediate

I11. Abstract class or interface: how do you choose?

Use an abstract class for an is-a family that shares state or code, and needs constructors or non-public members. Use an interface for a capability that unrelated classes can have (Comparable, Runnable), or whenever a class needs several of them. Since Java 8 interfaces can carry default behaviour, so when in doubt start with an interface.

I12. Can you override static, private or final methods?

None of them. Static methods are hidden, not overridden: the call is chosen by the reference type. Private methods aren't inherited, so a same-named child method is a new method. Final methods are explicitly closed to overriding.

I13. Parent p = new Child(); What can you call on p, and what runs?

You can call only what Parent declares; the compiler checks the reference type. For an overridden method, Child's version runs (dynamic method dispatch). Fields are not polymorphic: p.field reads Parent's field. Child c = new Parent(); doesn't compile, and forcing it with a cast throws ClassCastException.

I14. Static vs dynamic binding?

Static (early) binding happens at compile time: overloaded methods, static, private and final methods, and all field access. Dynamic (late) binding happens at runtime, for overridden instance methods, through the JVM's virtual method table.

I15. this vs super?

this is the current object: it tells fields from parameters, calls sibling constructors with this(...), and can be passed or returned. super is the immediate parent: super(...) calls its constructor (first statement, inserted automatically if missing), super.m() calls its version of a method, and super.x reaches a hidden field. Neither can be used in a static context, and there's no super.super.

I16. == vs equals()? What is the equals/hashCode contract?

== compares references (the same object?); equals compares meaning, if the class overrides it. Contract: equal objects must have equal hash codes, because hash-based collections find the bucket by hashCode before calling equals. Override both together, using the same fields, and handle null and other types in equals.

I17. Association, aggregation, composition?

Association: one object uses another, and both live independently (teacher and student). Aggregation: a weak has-a, where the part is passed in and survives the whole (department and professors). Composition: a strong has-a, where the part is created and owned by the whole and dies with it (house and rooms).

I18. What is the diamond problem, and how does Java handle it?

If D inherits from B and C, which both inherit from A, which version of A's method does D get? Java forbids multiple class inheritance, so it can't happen with classes. With interface default methods it can. Rules: a class method wins over any default; a more specific interface wins; otherwise D must override and can pick one with B.super.m().

I19. Shallow vs deep copy?

A shallow copy duplicates the object but shares the objects its fields point to; Object.clone() is shallow. A deep copy also copies those inner mutable objects, so the two are fully independent. Prefer copy constructors over clone(), which needs Cloneable, a cast and a checked exception, and skips constructors.

I20. Can an abstract class have a constructor? Why, if you can't instantiate it?

Yes. It runs through super(...) whenever a concrete subclass is created, and initialises the fields the abstract class declares. What's illegal is an abstract constructor, and abstract static or abstract final methods.

I21. Static nested class vs inner class?

A static nested class doesn't need an outer object (new Outer.Nested()) and can't touch the outer object's instance fields. An inner class is tied to an outer instance (outer.new Inner()), can read its private fields, and keeps a hidden reference to it. "Static" there doesn't mean the nested class's objects share fields.

I22. Why are String and the wrappers final and immutable?

Security and safety: strings are used for class names, file paths and keys. If they could change, or be subclassed with altered equals/hashCode, a HashMap key could silently break and validation could be bypassed. Immutability also makes them thread-safe and lets the JVM share literals (the string pool) and cache small Integer values.

Advanced

A23. When should you prefer composition over inheritance?

When the relationship is has-a, when behaviour must change at runtime, or when inheriting would force you to disable a parent method. That last case breaks Liskov: Penguin extends Bird with a throwing fly(). The NiceCar example swaps its engine object at runtime, which inheritance can never do.

A24. Explain SOLID with a violation for each.

S: a User class that also emails and saves to the database. O: an if/else on payment type you edit for each new type. L: Square extends Rectangle breaking setWidth. I: a fat Printer interface forcing fax(). D: new MySQLDatabase() hard-coded inside a service instead of an injected interface.

A25. Write a thread-safe Singleton.

Simplest: enum Registry { INSTANCE; }, which is also safe against serialization and reflection. Lazy: the holder idiom, with a private static class Holder { static final X INSTANCE = new X(); }. Or double-checked locking with a volatile field. The basic lazy null-check version isn't thread-safe.

A26. How do you make a class immutable?

Make the class final. Make every field private final, set in the constructor. Provide no setters; "modifiers" return new objects. Defensively copy mutable inputs (List.copyOf), and never expose mutable internals. Or use a record, and still copy mutable components in its compact constructor.

A27. Checked vs unchecked exceptions, and how they interact with overriding.

Checked exceptions (Exception but not RuntimeException) must be caught or declared, and represent recoverable conditions. Unchecked ones (RuntimeException) usually signal bugs. An override may throw fewer or narrower checked exceptions than the parent, never new or broader ones. Unchecked exceptions are unrestricted.

A28. What is type erasure? What does ? extends vs ? super mean?

Generics are checked at compile time, then erased to Object or their bound, so there's no new T(), no List<int>, and no overloading that differs only in a type argument. PECS: use ? extends T for a source you read from (producer) and ? super T for a sink you write to (consumer).

A29. Records and sealed classes: what problems do they solve?

Records remove the boilerplate of data classes: they generate the constructor, accessors, equals, hashCode and toString, and are final. Sealed classes restrict who can extend a type (permits), so a switch over its subtypes can be checked for completeness by the compiler. Together they model fixed sets of data shapes cleanly.

A30. GFG also asks about destructors, friend functions and virtual functions. What's the Java answer?

Those are C++ ideas. Java has no destructors: the garbage collector reclaims memory, and resources are released with try-with-resources (finalize is deprecated). There are no friend functions: package-private access is the closest equivalent. Every non-static, non-private, non-final Java method is effectively virtual, and an abstract method is Java's "pure virtual" function.
